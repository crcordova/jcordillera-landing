# P1.3 — Plan de desarrollo de fichas de especie

> **Estado:** plan detallado; todavía no implementado.
> **Objetivo:** publicar páginas estáticas `/planta/[slug]` para las especies
> aprobadas, usando datos verificables, imágenes en Cloudflare R2 y CTA a
> WhatsApp. No crear e-commerce ni una herramienta de administración.
> **Leer junto con:** `AGENTS.md`, `CLAUDE.md`, `agents/02-plan-seo-tecnico.md`
> § P1.3 y `agents/05-geo-llm.md`.

## 1. Estado actual y alcance

- `catalogo-plantas.html` contiene 119 tarjetas y presenta nombres comunes,
  nombres científicos, categoría, descripción, una ficha de características
  variables y variantes con precio. El HTML está rotulado “Temporada 2025”; sus
  precios y disponibilidad deben confirmarse antes de publicarlos como actuales.
- `src/data/tienda.js` ya contiene 119 registros / 161 variantes. Sus `id`
  funcionan como identificadores del catálogo y son la mejor referencia para
  conservar slugs existentes y enlaces.
- El HTML de referencia carga fotografías dinámicamente desde Pixabay en el
  navegador. Las etiquetas `<img>` empiezan sin URL propia; esas llamadas y sus
  imágenes no son una biblioteca estable para producción.
- Hoy `/tienda/[categoria]` entrega todos los productos a `TiendaClient`, aunque
  el visitante esté viendo una categoría. P1.3 corrige esto para las páginas de
  categoría.
- La página nueva es un Server Component estático. Una visita a una especie no
  debe descargar el catálogo completo ni consultar R2 para obtener los datos.

**Incluido:** extracción del catálogo, contrato JSON, reglas de alta/retiro,
slugs, imágenes públicas en R2, páginas, enlaces internos, sitemap, metadata,
WhatsApp, rendimiento, seguridad del media endpoint y validación.

**Fuera de alcance:** administración visual, sincronización de stock, checkout,
pagos, edición de inventario, enriquecimiento agronómico automático y publicación
de datos no aprobados.

## 2. Decisiones de arquitectura

### 2.1 Fuente de datos y responsabilidad de cada archivo

1. **Entrada para la primera migración:** `catalogo-plantas.html`.
2. **Referencia de compatibilidad:** el catálogo actual de `src/data/tienda.js`,
   sobre todo sus IDs, categorías, variantes, precios y helpers existentes.
3. **Salida propuesta:** `src/data/plantas.json`, versionado en GitHub. El JSON es
   texto liviano; las fotografías son los archivos que se guardan fuera del repo.
4. **Fuente canónica después de aprobar la migración:** `plantas.json`. El HTML
   queda como referencia del catálogo importado, no como segundo lugar que haya
   que editar en paralelo.
5. Los helpers que consumen tanto Server como Client Components se separan del
   archivo grande de datos. En particular, los componentes de tarjeta no deben
   importar el catálogo completo para usar una función de formato o WhatsApp.

El build lee el JSON local y produce HTML, metadata y sitemap estáticos. No se
hará una llamada por visita a R2 para buscar el catálogo. Si en el futuro se
decide que el JSON también viva en R2, se deberá descargar y validar durante el
build; cada cambio seguirá requiriendo un nuevo deploy para regenerar las rutas.

### 2.2 Modelo de datos flexible

No usar propiedades obligatorias distintas para cada categoría. Por ejemplo,
árboles, arbustos, trepadoras y cubresuelos pueden tener características
diferentes. La interfaz renderiza cualquier número de pares de atributo y valor.

```json
{
  "id": "abelia-arbustiva",
  "nombre": "Abelia Arbustiva",
  "nombreCientifico": "Abelia grandiflora",
  "categoria": "arbusto",
  "descripcion": "Descripción factual tomada de la fuente aprobada.",
  "atributos": [
    { "nombre": "Sol", "valor": "Sol a semisombra" },
    { "nombre": "Altura", "valor": "1,5–2 m" },
    { "nombre": "Follaje", "valor": "Semi-persistente, verde brillante" },
    { "nombre": "Floración", "valor": "Verano–otoño" },
    { "nombre": "Riego", "valor": "Moderado" }
  ],
  "variantes": [
    { "tamaño": "B30", "bolsa": "bolsa 30 cm", "precio": 9500 }
  ],
  "imagen": "plantas/abelia-arbustiva/principal-v1.webp",
  "imagenes": [],
  "emoji": "🌿",
  "destacado": false,
  "publicada": true,
  "disponibilidad": "consultar",
  "actualizado": "YYYY-MM-DD"
}
```

Reglas del modelo:

- `id` es un slug único, persistente y global. Se conserva aunque cambie el
  nombre visible o la categoría.
- `atributos` es una lista opcional. Cada especie conserva solo los atributos
  respaldados por su fuente; también se conservan atributos no previstos.
- `variantes[].precio` es un número entero CLP; no guardar `"$9.500"` como texto.
- `imagen` y `imagenes` contienen claves relativas dentro del bucket, nunca
  credenciales ni URLs de administración. La UI puede mostrar emoji si no hay foto.
- `publicada` controla si se genera página, aparece en el catálogo y se incluye
  en el sitemap. Los borradores no se publican.
- `disponibilidad` no equivale a stock en tiempo real. Sin integración de
  inventario, el texto predeterminado es “Consultar disponibilidad por WhatsApp”.
- `actualizado` solo cambia cuando se edita esa ficha; se usa para `lastModified`
  del sitemap, no la fecha del build para todas las URLs.
- Se puede conservar `whatsappExtra` y otros campos actuales si se usan en el
  catálogo. El validador avisa antes de descartar una propiedad existente.

### 2.3 Imágenes y R2

Separar los binarios de medios de los datos:

```text
bucket público de medios/
└── plantas/
    └── <id-estable>/
        ├── principal-v1.webp
        ├── detalle-01-v1.webp
        └── detalle-02-v1.webp
```

- Crear un bucket dedicado exclusivamente a imágenes aprobadas para publicación.
  No guardar allí JSON privado, backups, originales privados ni llaves.
- Conectar un dominio propio de Cloudflare, por ejemplo `media.<dominio>`; no
  usar `r2.dev` en producción. La integración de Next.js limita `remotePatterns`
  al host de medios esperado.
- Mantener la base del dominio público en una variable de entorno pública porque
  forma parte de la URL de la imagen; nunca colocar credenciales de R2 en una
  variable `NEXT_PUBLIC_*` ni en el navegador.
- Preparar fotos comprimidas para web y dimensiones coherentes con los usos de
  tarjeta y ficha. Definir si la optimización la hará el pipeline de imágenes,
  Cloudflare o el optimizador de Next/Vercel después de probar costo, formatos,
  caché y calidad. No pagar dos optimizadores para la misma transformación.
- `next/image` sigue siendo obligatorio, con `fill` y `sizes`. La foto principal
  de ficha puede tener prioridad de carga; galería y tarjetas fuera de viewport
  deben cargar de forma diferida.
- Cambiar una foto creando una nueva clave versionada (`principal-v2.webp`) y
  actualizando el JSON. Así se puede dar caché larga sin que una imagen antigua
  quede pegada en CDN.
- El alt de una imagen describe la especie y la imagen real; no repetir keywords
  artificialmente. La foto es opcional y nunca bloquea el render de la ficha.

#### Riesgo de exposición y costo

Un bucket público significa que cualquier visitante puede descargar las URLs
públicas que conozca. La raíz no lista el contenido, pero eso no reemplaza el
control de acceso: los objetos son medios públicos. Las imágenes también pueden
ser enlazadas desde otros sitios.

Según la documentación oficial consultada el 2026-11-03, R2 Standard incluye al
mes 10 GB-month de almacenamiento, 1 millón de operaciones Clase A y 10 millones
de lecturas Clase B; el egreso directo desde R2 no tiene cargo. Sobre el tramo
incluido, la tarifa publicada para Standard es USD $0.015 por GB-month de
almacenamiento y USD $0.36 por millón de lecturas Clase B. Una descarga pública
autorizada sí cuenta como lectura; una solicitud rechazada por autenticación o
permisos no se factura como operación R2. Estos valores pueden cambiar y se
deben volver a verificar al implementar.

Controles requeridos antes de publicar:

1. Usar un **dominio personalizado** de Cloudflare. La URL `r2.dev` no es para
   producción y no ofrece las mismas reglas de caché, WAF y bot management.
2. Deshabilitar el acceso alternativo `r2.dev` si se habilitó. De lo contrario,
   el dominio público alternativo puede saltarse reglas aplicadas solo al dominio
   propio.
3. Configurar caché de borde explícita para los formatos de imagen usados,
   TTL largo para claves versionadas y revisar hit/miss. No asumir que todos los
   archivos se cachean automáticamente.
4. Usar las reglas WAF, controles anti-bot y limitación de tasa que estén
   disponibles en el plan de Cloudflare. Evaluar hotlink control sin bloquear
   navegación directa, el sitio ni crawlers legítimos.
5. Revisar mensualmente almacenamiento, operaciones de lectura, cache hit ratio
   y cualquier optimización/transformación facturada por separado. Configurar
   alertas disponibles en la cuenta; no asumir que hay un límite de gasto duro.
6. No exponer claves de escritura. Las credenciales S3/R2, si se necesita un
   proceso de carga automatizado, solo viven en secretos de CI o de un entorno
   servidor con permisos mínimos. Para esta fase la carga puede hacerse desde el
   dashboard, sin crear un uploader público.

Las imágenes pueden traer costos de otros servicios aunque el egreso de R2 sea
gratuito, por ejemplo transformaciones o el optimizador remoto de Vercel. El
piloto debe medir ambos lados antes de elegir el flujo definitivo.

Referencias oficiales:

- [R2 pricing](https://developers.cloudflare.com/r2/pricing/)
- [R2 public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/)
- [R2 limits y `r2.dev`](https://developers.cloudflare.com/r2/platform/limits/)
- [Cache de Cloudflare frente a R2](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/)

## 3. Normalización del catálogo con un agente especializado

Se usará un agente de extracción/normalización para preparar la primera
migración, no para tomar decisiones botánicas ni modificar el sitio directamente.

### Entrada y entrega

**Entrada:**

- `catalogo-plantas.html` como fuente principal de las características que
  contiene.
- `src/data/tienda.js` como catálogo actual de comparación y referencia de IDs,
  estructura de categorías, precios y mensajes existentes.
- `CATEGORIAS` para validar que las categorías del resultado existen.
- El contrato JSON de la sección 2.2.

**Salida candidata para revisión (no sobrescribir producción en el primer paso):**

- `plantas.candidato.json` con los registros normalizados.
- `informe-migracion-plantas.md` con conteos, correspondencia entre tarjetas e
  IDs existentes, campos omitidos y todas las diferencias entre fuentes.
- Una lista de registros ambiguos que requieren una decisión del dueño.

### Instrucciones obligatorias del agente

1. Leer solo contenido de catálogo: nombre, científico, categoría, descripción,
   filas de características y precio/tamaño/bolsa.
2. Tratar `.ficha .fi` como una lista variable de características. Limpiar el
   emoji decorativo del label si corresponde, pero preservar el nombre y el
   valor. No exigir que un arbusto y un árbol tengan los mismos campos.
3. Convertir cada fila de precio a variante con precio numérico CLP, preservando
   tamaño y descripción de bolsa.
4. Emparejar primero cada tarjeta con un `id` existente mediante nombre común,
   nombre científico y categoría. No cambiar ni regenerar slugs que ya se usan.
5. Para registros sin correspondencia inequívoca, proponer un slug normalizado,
   marcarlo como pendiente y no resolver colisiones automáticamente.
6. Comparar todos los campos coincidentes entre HTML y `tienda.js`. No decidir
   por cuenta propia qué precio o dato contradictorio es correcto; enumerarlo en
   el informe para revisión humana.
7. No inventar atributos ausentes, usos, disponibilidad, sinónimos ni texto SEO.
   Los campos desconocidos se conservan o se reportan, nunca se eliminan en
   silencio.
8. Marcar que el HTML indica temporada 2025. No presentar sus precios como
   vigentes en 2026 (o temporada posterior) hasta recibir confirmación del dueño.
9. Excluir CSS, JavaScript, filtros, HTML de presentación, consultas de búsqueda
   internas y URLs de Pixabay. No copiar credenciales, API keys ni el mecanismo
   que solicita fotos desde el navegador.
10. No editar `catalogo-plantas.html`, `tienda.js` ni componentes durante la
    extracción. La propuesta se valida y aprueba antes de convertirse en la
    fuente canónica.

### Revisión y validación del resultado

La normalización se acepta solo si:

- El conteo de tarjetas, categorías y variantes coincide con la fuente o cada
  diferencia está explicada en el informe.
- No hay IDs duplicados, categorías inválidas ni variantes sin precio numérico.
- No se perdió ninguna característica presente en una ficha del HTML.
- Cada registro corresponde a una tarjeta fuente y se revisaron los conflictos
  con el catálogo actual.
- Los precios, temporada y disponibilidad actuales están confirmados por el dueño.
- El agente no ha añadido datos botánicos o texto fabricado para completar campos.

Tras aprobación, promover `plantas.candidato.json` a `src/data/plantas.json` y
marcar el JSON como fuente de edición para altas y cambios posteriores. Los
helpers existentes se mantienen o adaptan sin duplicar datos.

### Higiene de la fuente HTML

`catalogo-plantas.html` incluye actualmente una clave de API de Pixabay en código
JavaScript del navegador y consulta ese servicio para cargar imágenes. Esa clave
ya es visible en el HTML y no debe copiarse al JSON, a Next.js ni al bucket R2.
Revisar su revocación/rotación con Pixabay y retirar del flujo de producción la
consulta dinámica. La migración de contenido no transfiere derechos sobre fotos:
subir a R2 solo imágenes propias o con licencia confirmada.

## 4. Ciclo manual de publicación y retiro

No se crea una herramienta de inventario. El flujo se conserva como edición de
datos + carga de imagen + deploy.

### Alta de especie

1. Confirmar nombre, nombre científico, categoría, variantes, precios y atributos.
2. Reservar un `id` global y estable; buscar duplicados antes de publicarlo.
3. Agregar la ficha a `plantas.json` con `publicada: true`, `disponibilidad:
   "consultar"` y fecha real `actualizado`.
4. Subir imagen optimizada opcional a `plantas/<id>/` en R2 y verificar su URL.
5. Ejecutar el validador y `npm run build`, revisar ficha, tarjeta, CTA y sitemap.
6. Desplegar. `generateStaticParams` recoge la especie publicada y la URL entra
   al sitemap automáticamente.

### Cambio o falta temporal de disponibilidad

- No prometer unidades en stock ni disponibilidad instantánea sin un sistema de
  inventario.
- Si una especie puede volver, conservar la página y mostrar texto temporal
  aprobado, además del CTA “Consultar disponibilidad”. No afirmar `InStock` en
  JSON-LD sin una fuente fiable de stock.
- Actualizar precios/variantes y `actualizado` cuando el dueño confirme el cambio.

### Retiro y cambio de slug

- Para una planta que deja de ofrecerse, actualizar `publicada: false`; no generar
  ficha nueva, no mostrarla en la tienda y quitarla del sitemap.
- Mantener un registro de slugs retirados. Si existe un sustituto realmente
  equivalente, crear redirección 301 al sustituto o a la categoría adecuada.
  No redirigir todas las plantas retiradas a la portada.
- Si no existe una sustitución útil, la URL termina en 404 y se retira de los
  enlaces internos. Conservar el slug en el historial evita reutilizarlo por error.
- No cambiar `id` por cambios editoriales de nombre/categoría. Si el cambio es
  inevitable, mantener una redirección permanente desde la ruta publicada.

## 5. Rutas, ficha y navegación interna

### Página `/planta/[slug]`

Implementar `src/app/planta/[slug]/page.jsx` como Server Component. No se necesita
un `layout.jsx` dinámico por especie: `generateMetadata` vive en `page.jsx`.
Usar Next.js 16 correctamente (`params` es Promise).

Responsabilidades de la página:

- Encontrar una especie publicada por su `id`; si no existe, responder con
  `notFound()`.
- Generar parámetros estáticos solo para registros publicados. Considerar
  `dynamicParams = false` para que el universo de rutas coincida con el catálogo.
- Generar title, description, canonical, Open Graph y Twitter únicos con los
  datos reales de esa especie; URL absoluta canónica en `jardincordillera.cl`.
- Renderizar un solo H1 con el nombre visible. Añadir nombre científico, precio
  de referencia, categoría, descripción, atributos presentes, variantes y
  mensajes de disponibilidad/WhatsApp.
- Renderizar atributos genéricamente desde `atributos`; una lista vacía no genera
  filas vacías ni valores inventados.
- Incluir breadcrumb visible con enlaces `Inicio → Tienda → Categoría → Planta`.
  La URL canónica se mantiene plana: `/planta/<id>`, aunque su categoría cambie.
- Añadir 3–4 especies relacionadas de la misma categoría cuando existan, con
  enlaces a sus fichas.
- Todas las llamadas de WhatsApp usan `getWhatsAppUrl(planta, variante)`.

### Enlaces de tarjeta

- En vista mosaico, foto, nombre y descripción llevan a `/planta/<id>`.
- En vista lista, el nombre lleva a la ficha.
- CTA principal y filas de tamaño/precio siguen siendo enlaces independientes a
  WhatsApp con su mensaje contextual actual.
- No envolver una tarjeta completa en `<Link>` mientras contenga enlaces de
  WhatsApp; eso crearía anchors anidados inválidos. Se usan regiones/enlaces
  separados, teclado accesible y nombres descriptivos.
- En la ficha, enlace de regreso a la categoría y las tarjetas relacionadas
  forman enlaces internos rastreables.
- Revisar `prefetch` si la lista contiene muchos enlaces a fichas: evitar que el
  navegador precargue decenas de rutas estáticas que el visitante no va a abrir.

### Separación de datos para el navegador

- En `/tienda`, mantener lo necesario para búsqueda y filtros globales, sin
  incluir textos editoriales o galerías grandes que no necesita una tarjeta.
- En `/tienda/[categoria]`, seleccionar las especies en el Server Component y
  pasar únicamente la categoría seleccionada al cliente. El selector de
  categoría debe navegar a las otras rutas de categoría; búsqueda y vista pueden
  seguir operando en el subconjunto actual.
- En `/planta/[slug]`, enviar/renderizar solo esa ficha y las 3–4 relacionadas;
  nunca serializar el catálogo completo a un Client Component.
- Separar funciones cliente puras (precio/WhatsApp) del módulo que importa JSON,
  para que una tarjeta no cause accidentalmente el bundle de todo el catálogo.

## 6. SEO, contenido y sitemap

- El contenido base debe ser visible en HTML del servidor; no depender de que un
  buscador ejecute JavaScript para conocer los datos de la especie.
- Cada ficha indexable lleva contenido específico de su planta. Combinar la
  descripción verificada, atributos particulares, presentaciones y precio. No
  repetir un párrafo genérico idéntico en las 119 fichas como sustituto de texto.
- `agents/05-geo-llm.md` recomienda texto original cercano a 80+ palabras para
  cada especie y prohíbe generación masiva sin revisión. Donde la fuente no dé
  contenido suficiente, solicitar validación/enriquecimiento al vivero antes de
  marcar la ficha como indexable; no rellenar con agronomía inventada.
- Canonical auto-referente por cada `/planta/<id>` y metadata apropiada para una
  página informativa/comercial de vivero, sin afirmar envío, stock o e-commerce
  que el negocio no ofrece.
- Actualizar `src/app/sitemap.js` para incluir especies con `publicada: true`,
  `priority: 0.7` y `lastModified` de `actualizado`. Excluir borradores y
  retiradas. Evitar usar la fecha actual del build como fecha de cambio de todas.
- No implementar JSON-LD `Product`/`Offer` en este paso. Si se propone en P2,
  revisar que precios y disponibilidad describan correctamente venta física y
  no declaren stock no medido; pedir aprobación al dueño, como exige P1.3 de `02`.
- Una URL en sitemap no garantiza indexación ni ranking. Revisar Search Console
  después del deploy para cobertura, duplicados, impresiones y consultas.

## 7. Fases de implementación

### Archivos previstos

- `src/data/plantas.json`: catálogo aprobado que se usa en producción.
- `src/data/tienda.js`: categorías y operaciones de catálogo existentes; mantener
  exports retrocompatibles mientras los componentes se migran.
- `src/lib/whatsapp.js` y `src/lib/formato.js`: helpers puros que pueden importar
  componentes cliente sin incluir accidentalmente todo el JSON.
- `scripts/validar-catalogo.js`: validador Node sin dependencias para IDs,
  categorías, precios, atributos, campos requeridos, conteos y claves de imagen.
- `next.config.mjs`: allowlist exacta de host de imágenes R2 para `next/image`.
- `src/app/planta/[slug]/page.jsx`: ficha, `generateStaticParams` y metadata.
- `src/components/planta/PlantaHero.jsx` + `.module.css`: identidad, foto,
  precio y CTA WhatsApp.
- `src/components/planta/PlantaInfo.jsx` + `.module.css`: descripción y
  render genérico de `atributos`.
- `src/components/planta/PlantasRelacionadas.jsx` + `.module.css`: enlaces a
  especies de la categoría.
- `src/components/tienda/ProductCard.jsx`, `ProductList.jsx` y
  `TiendaClient.jsx`: enlaces a detalle, separación del CTA y filtro por categoría.
- `src/app/sitemap.js`: entradas de plantas publicadas y su fecha real.

Se ajustan los nombres de componentes si el diseño existente aconseja una
composición más simple; estas responsabilidades no deben duplicar la fuente de
datos ni el flujo de WhatsApp.

### Fase A — Importar y aprobar los datos

1. Ejecutar el agente normalizador descrito en §3 sobre HTML y catálogo actual.
2. Recibir JSON candidato e informe de conflictos/cobertura.
3. Resolver con el dueño nombres, slugs ambiguos, diferencias de precio y fichas
   con datos incompletos.
4. Convertir el JSON aprobado en única fuente del catálogo; pasar las validaciones.

**Salida:** catálogo normalizado, conteos conciliados, atributos completos tal
como están documentados, IDs estables y reglas de actualización acordadas.

### Fase B — Preparar medios R2 con piloto

1. Crear/verificar bucket dedicado y dominio personalizado.
2. Confirmar acceso público solo para medios aprobados; desactivar `r2.dev` de
   producción y mantener llaves de escritura fuera del frontend.
3. Subir unas pocas fotos optimizadas de plantas representativas.
4. Configurar `remotePatterns`, caché y métrica de consumo; escoger la ruta de
   optimización (Next/Vercel o Cloudflare/archivo preoptimizado) con mediciones.
5. Verificar que una URL pública carga, el bucket no lista contenido y que una
   ficha sin imagen usa el fallback sin generar solicitudes de optimización
   repetidas a un archivo inexistente.

**Salida:** política de nombres, formato/tamaño, dominio, caché y optimización
probados antes de subir el resto de fotografías.

### Fase C — Implementar la página de especie

1. Crear la ruta dinámica estática y la metadata.
2. Construir `PlantaHero`, `PlantaInfo` y tarjeta de relacionados con CSS Modules,
   componentes Server por defecto y `next/image` para fotos.
3. Pintar de manera genérica cero, uno o varios atributos.
4. Reutilizar el helper de WhatsApp; CTA y precio/variante conservan el flujo
   actual.
5. Enlazar foto/nombre/descripción del catálogo a detalle, manteniendo aparte
   las acciones a WhatsApp.

### Fase D — Enlazado, rutas y payload

1. Actualizar `ProductCard` y `ProductList` sin anidar enlaces.

## 8. Criterios de aceptación y QA

### Datos y rutas

- [ ] Los conteos del JSON aprobado se concilian con los registros fuente o sus
  diferencias están documentadas.
- [ ] No hay IDs repetidos, nombres de categoría inválidos ni referencias a
  imágenes fuera del dominio/árbol de medios definido.
- [ ] El build genera exactamente las rutas publicadas aprobadas.
- [ ] Una ficha desconocida o retirada no se genera; las redirecciones antiguas
  funcionan donde se definió reemplazo.

### SEO

- [ ] Cada ruta publicada sirve HTML con un H1, title, description y canonical
  propios; la ficha se entiende sin ejecutar búsqueda client-side.
- [ ] `/sitemap.xml` incluye solo fichas indexables/publicadas y usa la fecha de
  actualización correcta.
- [ ] Navegación desde tienda/categoría/relacionadas no deja fichas huérfanas.
- [ ] Contenido factual revisado; no hay atributos inventados ni afirmaciones de
  stock no sustentadas.

### UI y conversión

- [ ] Foto/nombre/descripción llevan a la ficha; los CTA de WhatsApp y las filas
  de precio abren `wa.me` con planta y variante correctas.
- [ ] No hay `<a>` anidados; los links funcionan con teclado y lector de pantalla.
- [ ] Ficha con imagen y sin imagen se ve bien en móvil y desktop.
- [ ] Atributos variables se muestran sin filas vacías y sin componentes por
  categoría duplicados.
- [ ] Breadcrumb, enlace de vuelta y relacionadas no apuntan a slugs inexistentes.

### Rendimiento, imágenes y operación

- [ ] `npm run build` y `npm run lint` pasan.
- [ ] Las páginas de especie no serializan el catálogo completo en props cliente.
- [ ] Las páginas de categoría no pasan productos de otras categorías.
- [ ] `next/image` usa `fill` + `sizes`; imagen principal optimizada sin cargar la
  galería completa al abrir la ficha.
- [ ] En producción, verificar `Content-Type`, caché, respuesta 200, formato y
  tamaño de las imágenes desde el dominio R2.
- [ ] Revisar logs/analytics de Cloudflare y consumo de R2/optimizador tras el
  piloto; confirmar que el caché reduce lecturas repetidas.
- [ ] Verificar `click_whatsapp` en GA4 desde una ficha y conservar mensajes.
